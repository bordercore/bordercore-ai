# Hermes Memory in Bordercore AI

Hermes is used by Bordercore as a long-term memory sidecar. It recalls relevant
memories before inference and reviews completed exchanges for durable facts
afterward. The model selected in the Bordercore UI still generates every
visible response.

Hermes's built-in memory is deliberately compact and curated. It is best used
as a persistent working-relationship profile, not as a complete conversation
archive.

## Useful applications

### Personal response preferences

Memory can preserve preferences that should apply across models and sessions:

- Concise or detailed responses
- Commands before explanations
- Preferred languages, frameworks, and testing tools
- Formatting and accessibility preferences
- When the assistant should ask before suggesting paid services

Examples:

```text
Remember that I prefer concise answers with actionable commands first.
Remember that Python examples should use type hints, uv, and pytest.
```

### Bordercore environment knowledge

Durable environment facts reduce repeated discovery and prevent advice for the
wrong system:

- Bordercore runs on `deepvirtual`.
- The production GPU is an RTX 3090.
- Python dependencies are managed with `uv`.
- Hermes listens only on a loopback interface.
- The Bordercore web application uses HTTPS port 5010.
- Deployment uses systemd user services.

### Project conventions

Hermes can retain conventions that should influence future work:

- Preferred test, lint, and formatting commands
- Documentation requirements
- Commit-message and branching conventions
- Files that must be reviewed after configuration changes
- Operations that require explicit approval

Example:

```text
Remember that Bordercore changes affecting setup or configuration must also
update the README.
```

### Corrections and learned safeguards

Corrections and workarounds are especially valuable because they prevent
repeated mistakes:

- Do not use `sudo` for user services.
- Do not infer `deepvirtual`'s GPU from the development machine.
- The frontend `package.json` is under `webapp/`.
- Hermes secrets belong in the owner-only systemd environment file.
- Never retain synthetic verification facts as user memories.

### Recurring task defaults

Memory can remove small decisions from recurring workflows:

- Inspect both Bordercore and Hermes services during deployment checks.
- Use a preferred local model unless another model is selected.
- Keep the first paragraph of voice responses brief.
- Prefer official documentation when researching software.

### Project direction and priorities

Store durable architectural decisions rather than an entire backlog:

- Agent Memory is a high-priority Bordercore integration.
- The model selected in the UI generates the visible answer.
- Hermes is a memory sidecar, not the primary chat model.
- Memory failures must not prevent ordinary chat.
- Local inference is preferred when practical.

### Cross-mode continuity

The same memories can improve typed conversations, voice conversations, local
models, and hosted models. A preference learned during a voice exchange can,
for example, influence a later response generated by Qwen or OpenAI.

### Lightweight personal-assistant context

Reasonable profile information includes:

- Timezone
- Preferred units and date format
- General working hours
- Frequently referenced project names
- Preferred programming languages
- Communication and accessibility preferences

Avoid sensitive identifying information unless storing it is deliberate and
necessary.

## What not to remember

Hermes memory should not contain:

- API keys, passwords, tokens, private keys, or other credentials
- Synthetic verification facts
- Temporary file paths or one-off debugging state
- Full logs, documents, datasets, or source files
- Facts that can be easily rediscovered from the repository
- Every question the user asks
- Detailed task or conversation history
- Incidental or short-lived personal details

Hermes's built-in memory does not silently compact itself when full. Keeping
entries selective, short, and current is therefore important.

## Recommended starter memories

```text
User prefers concise answers with actionable commands first.

Bordercore runs on deepvirtual; the production GPU is an RTX 3090.

Bordercore uses uv for Python dependency management and pytest for tests.

The model selected in the Bordercore UI must generate the visible response.
Hermes is used only as a memory sidecar.

Memory operations must fail open and must never store credentials, secrets,
temporary test facts, or incidental conversation details.
```

## Isolation and multi-user use

Hermes's built-in `MEMORY.md` and `USER.md` stores are files under
`~/.hermes/memories/`. A Hermes session key can scope provider sessions, but it
should not be treated as strong per-browser isolation for the built-in files.

The current single-user Bordercore installation can reasonably begin with
built-in memory. A multi-user deployment should instead use one of these
designs:

- A separate Hermes profile and home directory for every user
- An external memory provider with enforceable user-level isolation
- Bordercore-owned storage keyed to authenticated user identities

Hermes supports external memory-provider plugins such as Honcho, Mem0,
Hindsight, OpenViking, Supermemory, and others. These can provide richer
semantic retrieval and session-specific context, but introduce additional
deployment, privacy, and cost considerations.

## Recommended next feature

Add a **Manage Memory** screen to Bordercore that lets the user:

- Inspect stored memories
- See whether an entry is a user preference or an environment/project fact
- Correct an outdated entry
- Delete an individual entry
- Clear all memory
- Disable automatic storage while retaining recall

Explicit inspection and deletion controls are important because conversational
memory decisions can occasionally be incorrect or overly broad.
